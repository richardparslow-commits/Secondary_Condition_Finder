# Audit issues — ordered by priority

Compiled from the committed Security / Systems / VA Lighthouse production-readiness audit (`docs/security-va-production-audit-2026-10-04.md`), the security and architecture audit (`docs/security-architecture-audit-2026-10-07.md`), the accessibility evidence report (`docs/accessibility-audit.md`), the CRG redundancy triage (`docs/crg-redundancy-triage-2026-10-04.md`), the external/manual gates register (`docs/external-manual-gates-status.md`), the catalog-identity admission record (`docs/catalog-identity-admission.md`), the ME-17 ledger join fix (`docs/security-architecture-audit-2026-10-07.md §GATE-01`), and the repository knowledge-base validation state.

Priority labels reuse the audit convention:
- **P0**: ability, scope, or compliance gate the repository itself cannot close from code alone — not automatically a remotely exploitable critical vulnerability.
- **P1**: high-impact correctness, availability, privacy-assurance, or usability defect.
- **P2**: lower-impact correctness, coverage, or assurance gap; often disclosed rather than silently fixed.

Where a finding is marked `FIXED (local)`, it landed in committed code and has a regression suite. Where it says `still open`, `external`, `manual`, or `review-pending`, the repository has recorded the gap honestly rather than re-labeling it closed.

## P0 — scope, access, and compliance gates the repository cannot close itself

### 1. Veteran-specific integrations were requested but are absent (`B01`, security-va audit)

- The requested combined Disability Rating / Benefits Claims / Benefits Intake scope implies implemented integrations. The current product states that it does not connect to a veteran account or submit claims, and public Benefits Reference Data is administrative reference information, not an authenticated individual's ratings or claims.
- No OAuth authorization endpoint, callback, PKCE verifier transaction, state validation, token exchange/refresh/revocation lifecycle, or veteran identity-bound session existed at audit time for those capabilities.
- This is missing capability, not proof that an existing OAuth flow is vulnerable.
- **Repository posture:** keep the public-reference transition separate; choose and confirm eligible API versions/grants with VA before implementing veteran-specific flows. Addendum 2026-10-10: sandbox-only integration code has since landed (sealed account session store, `va-account` OAuth routes, `/api/auth/*` thin adapters, an unwired restricted-API HTTP client) — still no production grant, still disabled by default, still read-only sandbox scopes; the production half of this item is unchanged and externally blocked.

## P1 — high-impact correctness, availability, privacy, or usability defects

### 7. Recommendation aggregation is still order-dependent on valid synthetic inputs (`B05`, security-va audit; `FIXED (local)`)

- Discovery order can change ranking, contributing-primary/provenance/consensus presentation. The contract claims order-invariant aggregation, but the direct accumulator, path accumulator, and final score derivation did not separate direct contributions from paths and aggregate each collection before choosing the documented score/provenance policy.
- Two valid synthetic fixtures (`diagnosedConditionIds: [target]`) reproduce different outcomes for `[A, B]` versus `[B, A]`.
- **Test blind spot:** order-invariance tests omit `diagnosedConditionIds`, and the path composer requires a diagnosed target, so those tests do not activate the mixed direct/path cases they claim to protect.
- **Repository posture:** fixed in code with regression tests; not yet independently full-corpus-quantified here.

### 8. Distributed cooldown recovery is unfenced and Retry-After fidelity was not supported (`B06`, security-va audit; `FIXED (local)`)

- Outcome recording reset local circuit state and published shared recovery on every success, regardless of whether the success was an admitted probe.
- Shared recovery unconditionally deleted the open marker.
- A shared marker stored only state/openedAt and was compared against a fixed 60-second gate; a caller-supplied longer cooldown was not preserved.
- Local Retry-After clamped to 1–60 seconds; a longer upstream cooldown was shortened.
- **Repository posture:** fixed in code with coordination and fleet regression tests.

### 9. Shared coordination had false-success and ownership races (`B07`, security-va audit; `FIXED (local)`)

- Cooldown publication reported success on transport HTTP 200 even when the command payload carried an error; shared recovery could report transport success for marker deletion.
- Fetch-release and probe-release compared a token via GET then issued a separate DEL, so a lease replaced between those commands could be deleted by the old owner.
- A fetch lease was 45 seconds while a logical fetch could make multiple attempts plus backoff and coordination/write time, so the code's own documentation correctly calls it best-effort deduplication rather than a quota safety control. The lease is now 120 s (`VA_SHARED_FETCH_LEASE_MS`), sized to cover three 30 s attempts plus inter-attempt backoff and the shared write, so a legal winner can no longer be outlived by a contender's duplicate fetch.
- **Repository posture:** fixed in code using atomic compare-and-delete ownership and command-result validation.

### 10. Privacy statements contradict actual events; some error channels bypass redaction (`B08`, security-va audit)

- Privacy §3 and §7 say no workflow/recommendation event history is persisted through an application event logger. The auditLog module emits workflow action/status/route/count events, recommendation execution emits counts/duration, and the structured logger writes timestamped records for platform ingestion. A synthetic probe log contained these recommendation events.
- The audit found persistence error paths that directly logged parser/upstream exception text, client error boundaries that emitted exception content, and a LangSmith trace wrapper whose rejection callback could stringify arbitrary errors. The legacy secondary persistence-action module from that audit is no longer present following the browser-local migration.
- **Repository posture:** fixed locally at reviewed application sinks. Health checks return fixed per-component failure details and a content-free 503 fallback; bundled JSON parsing, catalog/KB/exposure/regulatory validation, graph-loader diagnostics, startup warmup failures, and LangSmith recommendation failures no longer serialize parser/error content. Regression tests plant sentinel diagnostics and verify they do not cross those boundaries. Operational action/count/status events remain intentionally logged and are documented as event logging, not a medical-record database.
- **Still open:** inspect actual collector/host retention, IP/request correlation, access controls, export paths, and any enabled LangSmith configuration against the deployed host. No deployed-host or third-party collector review was performed here, and event logging is not absent.
- **Inventory proof (code side, 2026-10-10):** `tests/logging-sink-inventory.test.ts` pins the complete application sink set against the working tree — 8 reviewed logger clients through the single redacting choke point, 3 audited `auditLog` routes/actions, 13 fixed-string direct-console sites (shapes governed by the PHI boundary suite), LangSmith wiring confined to one server-only module with zero `src/` callers (unreachable in production; export defaults off), OTel meters in exactly 3 no-op-without-collector modules with `registerOTel` never called, and the `/api/csp-report` intake verified to never log raw bodies (content-free 204/429 only). A new sink fails CI instead of shipping silently. Privacy §3 documents the operational events as event logging.

### 12. Browser-local OCR was broken by the production Trusted Types policy (`B04`, security-va audit; `FIXED (local, browser-verified)`)

- **Repository posture:** fixed by preferring a same-origin worker path, retaining strict URL/body policy, and browser-testing under the actual production headers. CSP/Trusted Types were not weakened.

Remaining production gates are the other findings (COMP-01 VA/Section 508 acceptance, SEC-02 trusted ingress, SEC-01 deployed-native verification).

### 14. Health can report healthy without the real production workflow secret (`REL-04`, architecture audit; `FIXED (local)`)

- The health endpoint previously tested crypto with an ephemeral probe secret independent of production config, so a production deployment without a usable workflow session secret could answer healthy.
- **Repository posture:** fixed so `components.workflowSession` reports the configured secret's round-trip readiness and gates `healthy`; a deployment that cannot seal and reopen a real workflow session answers 503. The recorded follow-up is retired 2026-10-10: `workflowSessionSecret()` no longer reads the legacy `SECONDARY_WORKFLOW_SESSION_SECRET` fallback, so the seal path and the readiness probe resolve the primary secret identically. ### 15. VA public search routes and identity policy had coverage/ingress gaps (`SEC-02`, architecture audit; `partially remediated (local)`)

- Inbound rate limiting originally matched only `/va-forms`, `/va-reference`, `/presumptive/results`, and `/secondary/suggestions`, missing `/va-forms/finder`, `/va-reference/service-branches`, `/secondary/evidence`, and `/presumptive`, which also reach reference loaders.
- Client key extraction trusted the first `X-Forwarded-For` entry, so a hostname, path fragment, or fresh random token could become a bucket key, and an unusable `X-Forwarded-For` could mask a usable `X-Real-IP`.
- Missing identity previously skipped the limiter entirely, which could turn a per-IP allowance into a global cap under load.
- **Repository posture:** `/va-forms/finder` and `/secondary/evidence` added to the limiter; `HEAD` now consumes the same reference budget as `GET`; identity is now a validated IP literal or nothing; missing identity is bounded by a named shared ceiling instead of skipped; the trust decision and store regime are now reported, not assumed (2026-10-15: the reported policy also names the ingress **model** and the hop enforcement reads); `/api/health` exposes `components.rateLimit.identity|ceiling|store`. Bucket regime remains process-local and resets on cold start; no shared counter store is provisioned for inbound admission; trusted ingress verification and hosted/two-instance acceptance remain open.
- **Repository posture (2026-10-15): the trusted-ingress claim is a mechanism, not a label.** `RATE_LIMIT_TRUSTED_INGRESS` selects an ingress model and the model decides which hop is an identity: `set` (aliases `true`/`overwrite`/`platform`) reads the leftmost `X-Forwarded-For` hop with `X-Real-IP` fallback — the rule that used to be applied to every deployment — while `append`/`append:N` (N = 1..8) reads hop **N from the right**, which an appender writes after (never instead of) whatever the client sent, so the hop the client writes is never the key and `X-Real-IP` is not read at all (an appending ingress does not set it, and a value there is client-supplied); a request with fewer than N hops did not traverse every declared appender and is unattributed — charged to that surface's shared identity-less bucket rather than to a hop the client sent, and to the ceiling as well (item 30). An unset, unrecognised or out-of-range value stays **unasserted**, so a mangled claim cannot read as a verified ingress. `/api/health` `components.rateLimit.identity` reports `model`, `header`, `hop`, `hopsFromRight` and `fallback` beside the existing fields, which makes the claim auditable against what the ingress actually writes instead of a comment. Pinned by `tests/rate-limiter.test.ts` (47), a `declared ingress model (SEC-02)` group in `tests/api-route-rate-limit-coverage.test.ts` (57, driving the real `proxy()`, with both discriminating cases falsified by removing the claim from the proxy call) and `tests/deployment-readiness.test.ts` (20); the five focused proxy/rate-limit/runtime suites pass 146/146 and typecheck exits 0. The model's published limits are part of the record: a single-hop request is indistinguishable from one that never traversed the ingress, and declaring more appenders than exist turns a client-padded hop into the one that is read — so the claim is only as good as origin protection and an exact appender count.
- **Repository posture (2026-10-15, observability half): a refusal now says which budget refused.** The repository's own deployment-readiness note recorded that `chargeAdmission` computed the reason for a refusal — the shared admission ceiling or the client's own bucket — while nothing logged or returned it, so ceiling saturation was not directly alertable and a 429 count could not be treated as a capacity signal. `src/lib/observability/refusal-window.ts` keeps the last 15 minutes of inbound refusals (256 retained events, 12 reported surface rows) and `/api/health` reports them as `components.rateLimit.refusals` (`byBudget`, `ceilingShare`, `surfaces`, `evicted`, `since`, `lastRefusedAt`, `detail`), forwarded from the capability report rather than re-derived by the route; `src/proxy.ts` records each refusal against `method-post`, `reference-read` or the matched route policy's path. It stores the surface label and the budget **only** — never the client key — so no address reaches the public payload, and the 429 body still names no budget (readable without becoming a probing oracle). Pinned by `tests/admission-refusal-window.test.ts` (14 cases, five of which fail when the proxy's record call is removed); typecheck exits 0 and 379 tests across 16 suites pass, including the runtime-capability registry guard and the logging-sink inventory, which is unchanged because no logger was added. The reading's own limits are recorded with it: the window is per instance, resets on cold start, and never sees a refusal the edge WAF answered itself, so a zero is not "no refusals anywhere".
- **Repository posture (2026-10-15, third clause): the identity-less class no longer gets a larger allowance than an identified client.** Item **30** records the defect found while auditing this path and its fix; the unasserted default is deliberately unchanged there, so this bullet's open items are unaffected.
- **Still open on SEC-02 after this pass:** the claim is unverified at a real edge (no edge, hosted, direct-origin, two-instance or cold-start run), and counters remain process-local with no inbound shared store provisioned, so no deployment-wide quota is claimed.

## P2 — lower-impact correctness, coverage, or assurance gaps

### 16. Reference-search text has a URL, upstream, and cache-value exposure path (`A01`)

- The Forms Finder is a GET form allowing arbitrary 120-character text. The loader trims/bounds it, hashes the cache key, sends it as the configured VA query when live access is allowed, and stores the raw query inside the returned/cached view.
- A sensitive identifier accidentally typed there can appear in browser history, application/edge request URLs, upstream VA traffic, and shared cache values. Hashing a key is not encryption or removal of its value. ZIP/radius/type likewise appear in directory parameters and cached values; low-entropy ZIP hashes can be enumerated.
- **Repository posture:** fixed locally 2026-10-10 for the identifier slice: `loadVaFormsFinder` refuses whole-input identifier-like queries (8+ digits ignoring separators) before any upstream send or cache write and never echoes the raw value in the view, with 15 regression cases; short numeric fragments and mixed text still search. Cache-value slice closed 2026-10-10: live Forms views cache with `query: ""` and live locator views cache with `params.zip: ""` (keys were already hashed), re-attached after the cache tiers for display/prefill only, pinned by `tests/va-reference-cache-value-redaction.test.ts` (2 cases); matching directory records still repeat query/ZIP text as VA data by design. Still open (as of 2026-10-10): raw legitimate query text still travelled in GET URLs (with an explicit never-enter-identifiers page note and `autocomplete="off"`), upstream VA traffic, and host/CDN logs — log scrubbing unverified, not closable from code.
- **Repository posture (2026-10-12): the Forms Finder's search text is no longer URL-borne.** The finder's search is a Server Action ([`searchVaFormsFinder`](../src/lib/actions/va-forms-finder.ts)) whose text travels in the request **body** through the PHI-free action-input contract and returns the view as action state; the [page](../src/app/va-forms/finder/page.tsx) reads no query parameter at all, and the [surface](../src/components/va/VaFormsFinder.tsx) performs no navigation and no history rewrite. A reference-path **POST** is now charged to the shared reference-read budget in [`src/proxy.ts`](../src/proxy.ts), so moving the search off the URL did not move it off admission control (the method-scoped POST bucket alone would have). Pinned by [`tests/va-forms-finder-no-url-exposure.test.ts`](../tests/va-forms-finder-no-url-exposure.test.ts) — including a mounted submit proving the text reaches the action's `FormData` while `window.location` never contains it, and a refusal path that echoes neither value nor key — plus [`tests/va-forms-finder-search-surface.test.tsx`](../tests/va-forms-finder-search-surface.test.tsx) and a POST-admission case in [`tests/private-context-request-guard.test.ts`](../tests/private-context-request-guard.test.ts).
- **Repository posture (2026-10-12): the locator's lookup text is no longer URL-borne either.** The accredited-representative search is now a Server Action ([`searchAccreditedRepresentatives`](../src/lib/actions/accredited-representatives.ts)) that validates through the PHI-free action-input contract, returns the directory view **as action state**, and never redirects — so the ZIP does not enter the address bar, browser history, a copied link, or the navigation's request line. The three hosting pages ([`/secondary/suggestions`](../src/app/secondary/suggestions/page.tsx), [`/secondary/evidence`](../src/app/secondary/evidence/page.tsx), [`/presumptive/results`](../src/app/presumptive/results/page.tsx)) read no lookup query parameter at all and no longer load the directory view, and the rendered surface ([`AccreditedRepresentativeFinder`](../src/components/va/AccreditedRepresentativeFinder.tsx)) performs no navigation and no history rewrite; the URL-parameter error reader that fed the old `?error=` transport was deleted with it. Reference-path **POSTs** were already charged to the shared reference-read budget in [`src/proxy.ts`](../src/proxy.ts), so the lookup did not move off admission control. Pinned by [`tests/va-accredited-rep-no-url-exposure.test.ts`](../tests/va-accredited-rep-no-url-exposure.test.ts) (source pins plus action behaviour: state-not-redirect, allowlisted audit route, fixed refusal codes, no echo, no network use on refusal) and [`tests/va-accredited-rep-locator-surface.test.tsx`](../tests/va-accredited-rep-locator-surface.test.tsx) (a mounted submit proving the ZIP reaches the action's `FormData` while `window.location`/`document.URL` never contain it), with the browser journey updated to assert the results render **in place** with no `zip=` in the URL.
- **Still open:** the upstream VA requests (Forms search text and directory ZIP) still carry the lookup text as a query parameter by design. Host/CDN log retention for whichever requests the operator runs is **not established**: H-02 gate A was closed on 2026-10-15 by a recorded review of the hosting platform's published log terms with the account facts that were not read named and accepted ([#537](https://github.com/richardparslow-commits/Secondary_Condition_Finder/issues/537), recorded in [external/manual gates](external-manual-gates-status.md)), and a drain configured in that account would forward request paths *with* their query parameters. H-02 gate B ([#538](https://github.com/richardparslow-commits/Secondary_Condition_Finder/issues/538)) was closed the same day, and it settles the *scrubbing* half for every request path rather than only the OAuth callback: the platform documents no query-parameter redaction for its runtime logs or for a drain on any plan, so a logged or drained path carries its query string as sent. What gate B accepts is the OAuth callback request line, bounded by the fact that no live authorization code can exist while the sandbox config is absent; it is **not** an acceptance covering this item's lookup text, which stays open. The retention actually in force therefore stays an accepted, unverified residual rather than a code question.

### 18. Fixed-minute shared budget permits a boundary burst; upstream quota semantics unconfirmed (`A03`)

- The shared budget increments `floor(now/60000)`, permits 60, and sets a 120-second expiration, so 60 reservations just before the minute plus 60 just after admit 120 in a millisecond-spanning boundary interval. This is expected fixed-window behavior, not proof of a VA quota violation without the applicable consumer's rolling/fixed/reset semantics.
- At review time (2026-10-04) `ratelimit-remaining`/reset guidance was not used to adapt pacing; the consumer policy, environment, and credential-sharing arrangement were not supplied.
- **Repository posture (2026-10-14): the repo-controlled half is fixed; the VA-policy half remains external.** Admission is now a conservative rolling window: the current bucket's atomic `INCR` count is charged together with `ceil(predecessorCount × overlapWeight)`, so the reproduced 60-at-59,999 ms plus 60-at-60,000 ms burst admits **0** at the second boundary rather than 120, and pacing refills gradually (half a window in, half a budget) while an absent predecessor carries nothing. Counter replies must be non-negative **safe integers** — a synthetic `1.5` no longer authorises a slot — an error body is refused even when it carries a numeric result, and the counter's lifetime is validated, so an unconfirmed `EXPIRE` refuses the slot and deletes the key instead of leaving a lifetime-less counter in the store. Pinned by [`tests/va-consumer-budget-admission.test.ts`](../tests/va-consumer-budget-admission.test.ts) (12 cases, each falsified by restoring the pre-fix function) alongside the fleet storm, the outbound cap, and the shared-cache suites; see the [R-08 update](r08-audit-verification-addendum-2026-10-12.md#a03--still-open-fixed-window-and-command-validation-risks-persist).
- **Repository posture (2026-10-14, third pass): the reservation is one atomic server-side operation, and the bound is proven under concurrency.** The rolling rule used to be assembled from separate commands — `INCR` here, a `GET` of the predecessor there, an `EXPIRE` after — so the two terms were read at different instants and the predecessor term was, as this list recorded, "a separate read a concurrent reservation can observe stale". `reserveVaSharedConsumerSlot` now issues a single `EVAL` (`SHARED_CONSUMER_WINDOW_SCRIPT`) that reads the predecessor, increments the window, establishes the counter's lifetime, and applies the fence in one operation, so nothing can interleave inside a decision (one bounded exchange instead of up to three). A reservation whose window the store has already moved past is refused before it writes anything — the latency-released form of the boundary burst, where callers admit a window's budget while the previous window's calls are still in flight and then those calls admit theirs — and the counter's lifetime is established in the same atomic step, closing the old hole where a creating instance died or failed its `EXPIRE` and left a counter that could never expire. The reply is a named decision code (`VA_SHARED_CONSUMER_DECISION`) read strictly: an erroring, unknown, or unreadable reply, and an invalid predecessor, all fail closed. Pinned by [`tests/va-consumer-budget-concurrency.test.ts`](../tests/va-consumer-budget-concurrency.test.ts), which asserts from the store's own recorded timeline that 200 racing attempts admit exactly one budget, that a half-weighted saturated predecessor admits exactly half, that an out-of-order store cannot exceed the fence, and that a staged straggler is refused and leaves the straddle total at one budget (falsified by neutralising the successor fence); the sequential contract, including one command per lifetime and per decision, is pinned by [`tests/va-consumer-budget-admission.test.ts`](../tests/va-consumer-budget-admission.test.ts) (15 cases), and the 40-instance fleet storm still admits one window's worth of upstream traffic.
- **Repository posture (2026-10-14, second pass): the guidance item is consumed, one-way only.** The `ratelimit-remaining`/`limit`/`reset` headers the upstream sends about its own quota now charge the same window counter: `parseVaApiRateLimitGuidance` reads them under either accepted prefix and refuses every shape it cannot read exactly (fractional, negative, unsafe, `+`-signed, hex, exponent, word, or empty values; `remaining > limit`; and a `reset` outside `VA_API_RATE_LIMIT_RESET_MAX_SECONDS`, which rejects epoch-seconds rather than reading it as a delay), `planVaApiConsumerPacing` charges the difference between the budget and the stated remaining quota — scaled by the part of the window the upstream is still short for, in full when it discloses no reset — and `applyVaConsumerPacingGuidance` writes it as a strict `INCRBY` on the reservations' own key, applying and validating a lifetime when the charge created the counter. The correction is deliberately one-way: nothing in it can lower a counter, raise the budget, or extend a window, and a refused charge is a warning rather than a failed request. Pinned by [`tests/va-consumer-pacing-guidance.test.ts`](../tests/va-consumer-pacing-guidance.test.ts) (28 cases: every response shape, the charge arithmetic, the real store, and the real adapter; making the planner always decline fails 18 of them and deleting the adapter's call fails the 3 adapter cases).

### 30. Identity-less requests were given a larger allowance than identified ones (`SEC-02b`; discovered during the SEC-02 workstream 2026-10-15; `FIXED (local)`)

- **Severity and position.** The finding is P1-class — an availability/fairness defect in the primary defence-in-depth layer — but it is listed here at the end of the numbering because this list is append-only and existing entries are never renumbered, exactly as item 29 above was added when it was fixed (2026-10-14).
- **The defect.** `chargeAdmission` charged the shared admission ceiling and then, when a request carried **no usable identity**, returned that ceiling result as its decision. So an identity-less request was bounded by the shared ceiling — **6000** charges a minute by default (`RATE_LIMIT_UNATTRIBUTED_MAX`) — while the *same* request presenting a valid key was bounded by that surface's per-client limit, **5–30** a minute as shipped. Non-attribution was therefore cheaper than attribution: sending a junk or absent forwarding header was the best strategy available to a caller, and that traffic drew down the aggregate budget every honest request also pays into. Under a declared ingress model it was also self-contradictory, because the operator had asserted that every request traverses an ingress which writes the header, so such a request is not one of that deployment's clients — and the code treated it more generously than a client.
- **Why it matters.** The per-client limits are the fairness control; a bound that is larger for the traffic that refuses to identify itself makes the strictest part of the control optional on demand, and it converts "no usable identity" into an amplifier for exhausting the aggregate budget that honest traffic depends on.
- **Repository posture: fixed locally 2026-10-15.** Where an ingress model is declared (`resolveIngressClaim(env).model !== "unasserted"`), an identity-less request is charged to one shared **class bucket per surface, at that surface's own per-client limit** (`unidentifiedAdmissionKey(limiter.name)`, `UNIDENTIFIED_ADMISSION_KEY_PREFIX` = `unidentified:`), enforced by the same limiter object that enforces the per-client limit, so the class gets exactly what one client gets and the bound cannot drift from the reported budget. `AdmissionResult.refusedBy` gains `unidentified`, the window reports `byBudget.unidentified` (a non-zero count means the declared model and the edge disagree), and `rateLimitIdentityPolicy().unidentified` → `components.rateLimit.identity.unidentified` reports the policy in force (`ceiling` or `shared-per-client-bucket`). The class key cannot collide with a client key, because `resolveClientKey` returns a key only for a syntactically valid IP literal — pinned directly. Pinned by `tests/rate-limiter.test.ts` (52, was 47: one client's allowance for the class, one bucket per surface, the unasserted default unchanged, the class key unreachable from a header, the reported policy for both models), `tests/api-route-rate-limit-coverage.test.ts` (58, was 57: the real `proxy()` refuses the 31st identity-less request under `append` with the ceiling at 5000 untouched) and `tests/admission-refusal-window.test.ts` (16, was 14); restoring the pre-fix branch fails **4** of them, and the file was then restored and the suites re-run. `npm run typecheck` exits 0, changed-file ESLint exits 0, and **229 tests across 13 suites** pass, including the runtime-capability registry guard and the logging-sink inventory (unchanged — no logger was added).
- **Residual (not waived).** The ceiling is still charged for every attempt, so an attacker can still draw the shared aggregate budget down; this closes the allowance inversion, not aggregate exhaustion, and the edge WAF remains the capacity layer for that. Deployments that declare no ingress model keep the previous behaviour by design — without a declared ingress, an identity-less request cannot be told apart from an honest client of a deployment whose headers never arrive, and charging that population to one bucket at a client's own limit would cap it at one client's allowance, the global-cap defect the old shared `"unknown"` bucket represented. Nothing here is hosted evidence: no edge, direct-origin, two-instance or cold-start run was performed, and SEC-02's shared-store and hosted-acceptance halves stay open (item 15).
