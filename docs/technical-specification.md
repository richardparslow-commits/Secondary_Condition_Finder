# Technical Specification: Secondary Condition Finder

## Architecture Overview

Secondary Condition Finder is a Next.js 16 full-stack application deployed on Vercel, with an optional legacy Azure Static Web Apps fallback. The architecture separates concerns into three layers:

1. **Client Layer** (React 19, TypeScript): UI components, browser-local versioned workflow records, form handling, and in-browser document processing (PDF.js, Tesseract.js, Mammoth)
2. **Server Layer** (Next.js App Router): public authored data, bounded public-directory lookups, regulatory intelligence, health, and protected administration; no veteran workflow state mutation or storage
3. **Data Layer** (JSON in version control, disk-based runtime load): Condition catalog, knowledge base, presumptive categories, regulatory seed records

The application has no per-user workflow-history database and does not persist workflow context on the server. Secondary and presumptive workflow state is held in versioned, schema-bounded, tab-scoped browser `sessionStorage`; the server refuses private workflow fields if a caller submits them. Evidence documents are processed only in the browser. The separate, optional VA sandbox account experiment stores encrypted tokens server-side and is disabled by default.

## Technology Stack

### Runtime & Framework

- **Node.js 22.x** (LTS): Development and build runtime
- **Next.js 16.3.4** (App Router): Full-stack framework with edge-proxy support
- **React 19.2.8** (with React DOM): Client-side UI library
- **TypeScript 5.x**: Type-safe development language
- **Vercel Deployment**: Edge-accelerated CDN, serverless compute, middleware/proxy support

**Justification**: Next.js App Router provides server-side rendering, edge-middleware capabilities, and Vercel-native deployment integration. The architecture allows streaming server components, secure Server Actions (with automatic CSRF protection), and edge-level CSP nonce injection. TypeScript ensures type safety across schemas and API surfaces. Node.js 22 aligns with Vercel's LTS support policy.

### Data Validation & Schema

- **Zod 4.5.4**: Runtime schema validation for JSON catalogs, knowledge-base mappings, and API payloads
- **Strict Schema Enforcement**: All JSON files are validated at parse time; unknown keys are rejected; any schema violation fails the parse and is caught immediately

**Justification**: Zod's discriminated unions enable the CRG (Causal Relational Graph) classification, ensuring each suggestion explicitly declares its nexus pathway (DIRECT_CAUSATION, AGGRAVATION, ASSOCIATION_ONLY). Strict validation prevents silent data errors and ensures consistency across the catalog and its relationship graph (`npm run kb:validate` reports the live counts).

### Client-Side Document Processing

- **PDF.js (pdfjs-dist 6.3.289)**: PDF text extraction and rendering; no server transmission
- **Tesseract.js 6.0.1**: OCR for scanned PDFs; runs entirely in the browser using WebAssembly
- **@tesseract.js-data/eng 1.0.0**: English OCR language data
- **Mammoth 1.12.2**: DOCX archive parsing and text extraction

**Justification**: These libraries enable in-browser processing of evidence documents without transmitting raw bytes to the server. Tesseract.js WASM avoids backend OCR dependencies and keeps medical data in the user's browser.

### Styling & UI

- **TailwindCSS 4.x** (with @tailwindcss/postcss 4.x): Utility-first CSS framework
- **PostCSS 8.5.18+**: CSS transformation and plugin system
- **ESLint 9.x**: Code linting for consistency and security

**Justification**: Tailwind enables rapid, accessible UI development with WCAG 2.1 AA color contrast and semantic HTML. Utility-first approach reduces CSS surface area and makes style changes traceable in diffs.

### Testing & Code Quality

- **Vitest 4.1.11**: Fast unit/integration test runner (ESM-native)
- **Chrome / ChromeDriver**: E2E browser automation for CI workflows
- **npm audit**: Dependency vulnerability scanning

**Justification**: Vitest integrates with Next.js and TypeScript without extra configuration. Chrome/ChromeDriver tests real browser behavior for workflows and error boundaries. npm audit with `--audit-level=high` gates the CI on dependency vulnerabilities.

### Observability

- **@opentelemetry/api 1.9.0** (API only; the `@vercel/otel` SDK/exporter dependency was removed) — automatic trace export is disabled by policy (`src/lib/observability/telemetry-policy.ts`, enforced by `tests/telemetry-policy.test.ts`): no SDK provider is registered, so no framework span (with query-string URLs or exception text) can export; custom metric helpers remain lazy via `src/lib/observability/logger.ts` and stay no-ops until an exporter is deliberately added after the sanitization review
- **Structured JSON logger** (`src/lib/observability/logger.ts`): `createLogger(component, baseFields)` → `emit(level, component, message, fields)` as `JSON.stringify({timestamp:ISO, level, component, message, ...redactFields(fields)})` to `stdout`/`stderr` (`error|warn` → `console.error`, `debug` non-prod → `console.debug`, else `console.log`); `redactFields` strips `payload|rawText|evidence|cookie|secret|apiKey`; `isTestEnv()` quiets `debug` in `NODE_ENV=test|VITEST=true`; `Logger {debug,info,warn,error,child}`
- **OTel metric helpers** (best-effort, no-throw, lazy `eval("require")("@opentelemetry/api")` so tests without collector still pass): `getMeter("secondary-condition-finder")` → histograms `recommendation.latency.ms` / `evidence.parser.duration.ms` / `va.api.latency.ms` + counter `va.api.errors`; helpers `recordRecommendationLatency(durationMs, attrs)` (used in `recommend.ts`), `recordEvidenceParserDuration`, `recordVaApiLatency`, `recordVaApiError` (used in `sandbox.ts` on every VA path including `circuit-open`)
- **Sanitized audit trail** (`src/lib/observability/audit.ts`, `server-only`): `auditLogger = createLogger("audit")`, `AuditAction = "workflow-diagnosed-selected"|"workflow-service-connected-selected"|"workflow-ratings-selected"|"workflow-documents-context"|"workflow-completed"|"workflow-restarted"|"presumptive-service-history-saved"|"presumptive-service-history-cleared"|"regulatory-preflight-triggered"|"regulatory-preflight-unauthorized"`, `auditLog(action, {status:"success"|"failure"|"unauthorized", route?, count?, source?, environment?})` — drops `payload|rawText|evidence|cookie|secret|apiKey|diagnosed|serviceConnected|medications|treatments|history` loudly, `level = warn` on `failure|unauthorized` else `info` → `auditLogger[level]("audit:"+action, safe)`; wired in `src/lib/actions/accredited-representatives.ts` and `src/app/api/regulatory/preflight/route.ts` (since PRIV-01 stage 2 the six secondary steps run and persist entirely in the browser, and since 2026-10-08 the presumptive flow does too, so the `workflow-*` and `presumptive-service-history-*` actions remain in the union but are no longer emitted)
- **Server-side only**: No client-side analytics SDK; `error.tsx` boundaries log only `message+digest` via `console.error(JSON.stringify({timestamp, level:"error", component:"…-error-boundary", message, digest}))`

**Justification**: OpenTelemetry is industry-standard for distributed tracing. Vercel's OTel integration provides production visibility without a separate backend, and the JSON logger gives Vercel/OTel ingestors sanitized, structured lines with zero PII — raw evidence, workflow payloads, and secrets are redacted at the emit site. Lazy metric init keeps bundling light and tests green.

### Security & Configuration

- **server-only 0.0.1**: Enforces "use server" boundaries at build time; prevents accidental client-side import of server-only code
- **AES-256-GCM**: Authenticated encryption for the separate VA account sandbox's server-side token store; not used for secondary/presumptive workflow context
- **Zod secrets validation**: Configuration validation at runtime for server-only credentials and session-store secrets

### 2. Server Actions & Browser-Local Step Logic

- **Accredited-representative Server Action:** `src/lib/actions/accredited-representatives.ts` exposes the current sole workflow-area action, `searchAccreditedRepresentatives`, accepting only bounded public-directory lookup parameters through the PHI-free action-input contract (`src/lib/security/phi-free-action-input.ts`); it carries no veteran workflow context, and it returns the directory view **as action state** rather than redirecting, so the lookup ZIP never enters a URL (audit A01).
- **Browser-local secondary steps** (PRIV-01 stage 2 — no Server Action): `src/components/secondary/steps/*Step.tsx` (`use client`) read the browser-local record via `src/lib/secondary-workflow/use-browser-context.ts` (sessionStorage, `ready` gate, no swallowed errors), call the pure step functions in `src/lib/secondary-workflow/client-steps.ts` (`applyDiagnosedStep` / `applyServiceConnectedStep` / `applyRatingsStep` / `applyDocumentsStep` — the retired action logic including the `appendFormData` allowlists, `serviceConnectedAnswerDraft` carry, `parse*Selection` Zod + bounds, `invalid-context` bounds, and downstream resets), and persist through `src/lib/secondary-workflow/browser-context.ts` (Zod-bounded, versioned record under `secondary-condition-finder:secondary-workflow:v1`); a failed write maps to `context-too-large` and holds the user in place instead of navigating
  - Completion/restart: `src/components/secondary/SecondaryWorkflowCompletionActions.tsx` (`SecondaryWorkflowCompletionActions` / `SecondaryWorkflowRestartButton`) clears every registered browser-local key via `clearSecondaryWorkflowLocalState` and only then navigates to `/secondary` / `/secondary/diagnosed`; a failed cleanup surfaces `CleanupErrorAlert` instead of navigating
  - Transport conversion: `src/lib/secondary-workflow/transport.ts` (`workflowSessionToQueryParams`, `TransportableWorkflowState`) is the client-safe state↔form-params bridge used by the client steps and tests
  - Session crypto path: `src/lib/workflow-session-crypto.ts` provides AES-256-GCM seal/open primitives for the VA-account store when configured with its separate `VA_ACCOUNT_SESSION_SECRET`; `/api/health` probes the primitive ephemerally and `/runtime-readiness` checks the legacy primary `WORKFLOW_SESSION_SECRET` readiness marker. Neither secret protects research workflow state. The secondary sealed-cookie path and presumptive session module were deleted; the proxy (`src/proxy.ts`) appends expired path-scoped tombstones when requests still present `secondary-workflow-v2` (`/secondary` and `/`) or `presumptive-workflow-v1` (`/presumptive`).
- **Browser-local presumptive service history** (2026-10-08 — the retired `saveServiceHistory` Server Action and the sealed-cookie session module are both deleted): confirmed service locations, branches and dates are held in `src/lib/presumptive/browser-history.ts` under `presumptive-condition-finder:service-history:v1`
  - `persistServiceHistory(storage, draft, knownLocations)` validates through the same `serviceHistorySchema` (Zod) the retired action used, maps schema issues → the fixed codes `select-location`/`date-order`/`invalid-date`, keeps the authored-catalog location membership allowlist (now browser-side), and returns `storage-unavailable` when the tab refuses the write instead of navigating
  - `readPresumptiveHistory(storage)` treats a missing, corrupt, out-of-version or out-of-bounds payload as absent; `clearPresumptiveLocalState(storage)` clears the track's registered keys
  - `src/lib/presumptive/use-browser-history.ts` binds the record with `useSyncExternalStore` (cached snapshot, server snapshot “no history”); `src/components/presumptive/PresumptiveResults.tsx` reads it and runs `matchPresumptives` in the tab, while `/presumptive/results/page.tsx` reads no session and loads only public data
- **Browser-local scenario launcher** (PRIV-01 stage 2 — the scenario Server Action is retired): `src/components/ScenarioLaunchForm.tsx` (`use client`) looks the scenario up in the bundled `data/demo-scenarios.json`, validates it through `parseWorkflowState(workflowSessionToQueryParams(workflow), corpus.conditions)` against the public client corpus (`src/lib/client-corpus/`), clears every prior browser-local key, writes the validated state into the browser-local context record, then navigates to `/secondary/suggestions`; there is no scenario POST request (enforced by `tests/demo-scenario-launcher.test.ts`)

**Security Note**: The sole remaining Server Action, accredited-representative lookup, validates bounded public-directory `FormData` with Zod and Next.js CSRF protections; no private workflow selections accompany it. Secondary and presumptive records validate and persist in browser storage only, and the edge proxy refuses private-context request fields. Operational application and recommendation events do reach platform logs, so host retention/access must be reviewed rather than described as absent. PRIV-01's sentinel acceptance recorded zero occurrences in request URLs/bodies/headers/cookies, server HTML/RSC payloads, browser/server logs, or `.next/trace`; browser-local storage is the deliberate destination for bounded workflow records, while raw evidence bytes are not stored in the workflow record.

- **reference-cache-access.ts** (`server-only`): the single implementation of the two-tier read protocol every VA reference loader shares — `withVaReferenceCache(key, load, {enabled, decorateHit, ttlMs, cacheTrust, singleFlight})` reads process-local → shared → `load()`, promotes a shared hit into the process-local tier, and writes both tiers **only** when the loader resolves `cacheable: true`. Degraded `local-fallback` views are never cached, so an upstream outage cannot be pinned for a full TTL. `cacheTrust` is the loader's single trust policy (`cached-view-guard.ts`, A04): `accepts` gates the **process-local hit**, the shared hit, the contender-published hit, and the loader's own fresh view before either write; `degradedView` is what a fresh view failing `accepts` becomes — the labelled local fallback, never styled as live and never cached — so an out-of-bounds upstream response cannot be served as live VA data. `singleFlight` is the shared-miss coordination hook (`shared-single-flight.ts`); both are options of this one function so no loader can hand-roll either, and the two-part policy means a loader cannot validate a value without also naming what it serves instead. A rejected process-local entry is deleted, so later requests are misses rather than re-validating a known-bad value, and the rejection is disclosed as an `outcome`-coded operational log line. `VA_REFERENCE_NAMESPACES` is the one owner of key namespaces (`service-branches`, `forms-finder`, `forms-reference`, `disabilities`, `accredited-rep`) and `clearVaReferenceNamespace(ns)` clears exactly one owner's entries; namespaces are pairwise disjoint by construction
- **reference-shared-cache.ts** (`server-only`): optional cross-instance Redis-REST cache + fleet-coordination transport — `loadVaSharedCacheConfig` (https-only URL + token; canonical `VA_REFERENCE_SHARED_CACHE_*` or Upstash/Vercel aliases; default prefix `va:ref:`), `runVaSharedKvCommand` (single command, 750 ms whole-exchange deadline incl. body, 64 KiB bounded reply) used by the circuit modules. Value cache: keys restricted to the allowlisted namespaces `forms-finder:` / `forms-reference:` / `accredited-rep:` / `disabilities:` / `service-branches:` (`forms:` stays allowlisted for legacy in-flight values) with a conservative charset; reads are one atomic `MGET [cache-epoch, value]` accepting only `{envelopeVersion:2, epoch, value}` envelopes stamped with the currently observed epoch; writes read the epoch, are admitted against a finite per-namespace window budget (`VA_SHARED_KEY_WRITE_WINDOW_SECONDS=300`, `VA_SHARED_KEY_WRITE_MAX_PER_WINDOW=240` → ≤480 resident keys per namespace, ≤1,920 across the allowlist), then `SET … EX`, admitted only when the projected command reply fits the same 64 KiB budget minus `VA_SHARED_CACHE_REPLY_RESERVE_BYTES=512` — `vaSharedCacheReplyBytes(value, epoch)` measures the JSON re-wrapping the reader parses, so a value that would be dropped as oversized on read is refused instead of stored (A04; the earlier 256 KiB write bound was four times the read bound and silently unreadable in between). `bumpVaSharedCacheEpoch()` atomically advances the store-wide invalidation epoch (`INCR {prefix}cache-epoch`, absent marker = epoch "0") so every instance discards previously cached entries without a delete sweep; unreadable markers, unreachable coordinators, and exhausted budgets all fail closed (miss / skipped write). The same module owns the distributed consumer quota: `reserveVaSharedConsumerSlot` reserves every upstream attempt (including retries) against `VA_SHARED_CONSUMER_MAX_REQUESTS=60` per rolling `VA_SHARED_CONSUMER_WINDOW_MS=60000`, charging the current bucket's atomic count with `ceil(predecessorCount × overlapWeight)` so the end of one bucket plus the start of the next cannot admit twice the budget, and refusing any reply that is not a non-negative safe integer or any counter whose lifetime (`VA_SHARED_CONSUMER_COUNTER_TTL_SECONDS=120`) the store did not confirm

## Data Architecture

### Storage Model

- **Version-Controlled JSON**: All condition catalogs, knowledge-base mappings, presumptive categories, regulatory seed records, and demo scenarios are stored as `.json` files in the repository
- **Disk-Based Runtime Load**: At application startup (build time for static generation, runtime for dynamic routes), all JSON files are loaded, validated with Zod, and held in process memory
- **No product-data database**: catalogs and knowledge-base content are versioned JSON, not a database. The optional VA-account sandbox can separately use a configured remote session store; it is disabled by default.
- **Immutable Data Snapshots**: Each production deployment carries a specific knowledge-base snapshot; changes require a new deployment and CI validation

2. **Presumptive intake (browser-local)** → client validates service history against the authored location catalog, writes the versioned `sessionStorage` record, and navigates without a POST, workflow cookie, or server-side veteran context
3. **Regulatory preflight (scope-free)** → Step 5 establishes `RegulatoryPreflightSnapshot {snapshotId, registryDigest, freshness, reviewMode, legalRegulatoryConclusionsAllowed}` via a scope-free `prepareRegulatoryReview()` (identical for every visitor) before any recommendation output; `?regSnapshot={id}` carries the lock to Step 6 and is resolved via `loadLockedRegulatorySnapshot` / `missingLockedRegulatorySnapshot` fail-closed to `medical-only` (never silent substitute); relevance filtering runs in the browser (`relevantChangesForConditionIds` in `src/lib/regulatory/preflight/client-relevance.ts`) so the snapshot never sees the selections
4. **Recommendation (browser-local)** → `SuggestionsStep`/`EvidenceStep` load the public corpus at `/kb/client-corpus.json` (`src/lib/client-corpus/`, generated by `npm run build:client-corpus`) → `buildSecondaryRecommendationIntake(state)` → `recommend(catalog, kb, intake)` (`CONSENSUS_ORDER` `1/rank`, multi-primary accumulation, `HISTORY_SIGNAL_ALIASES` warnings, `findChronologyWarnings`/`findIntermediatePathways` 2-edge only, `matchIntakeContext` literal, Focus Engine `diagnosedConditionIds` strict filter `score desc→name`) → `buildNonServiceConnectedConditionResults` (every not-service-connected diagnosis as top-level row, `recommendation|null`)
5. **Evidence (browser-local only)** → `LocalEvidenceAnalyzer` (`pending[]` bounded queue, `busyRef||busy`, `extractLocalEvidenceDocument` dispatcher + `assertSafeDocxArchive`/`assertFileSize` + per-page `page.cleanup()`/`worker.terminate()` + `conditionTermPattern` matching) → `EvidenceAnalysis` → `sessionStorage:secondary-condition-finder:evidence-analysis:v1` via `serializeStoredEvidenceWithInfo` byte-budget (`trim oldest + queueMicrotask dropped warning`), `EvidenceGapCoverage` chips + `EvidenceGapReview` checklist (user-controlled `sessionStorage`/`localStorage`, never auto-satisfied)
6. **Export** → `ConsultationSummaryDownload` / `PrintReportButton` browser-generates checklist for supported relationships only (no raw excerpts / no `matchedIntakeContext` by default) — never persisted server-side

## Security Architecture

### Authentication & Authorization

- **Research workflows**: Public and unauthenticated; secondary and presumptive state stays in browser storage. The separately gated VA-account sandbox has its own explicit authorization and session flow; it is not a research-workflow account system.
- **VA account sandbox**: Separate optional, disabled-by-default, sandbox-only self-service account experiment at `/va-account`; it uses VA-issued sandbox OIDC authentication for bounded read-only rating-summary and claim-status operations, not production access, representative use, claim submission, or uploads. Registration and runtime gates are independent of the research workflows; see `docs/va-account-sandbox.md`.
- **Server Action CSRF Protection**: Next.js provides built-in CSRF protection for the bounded public-directory lookup action.
- **VA account Route Handler CSRF protection**: the separate sandbox `/va-account/oauth/*` mutation routes require exact same-Origin validation and explicit read-only consent for login start.
- **Private-context refusal**: the edge proxy rejects requests carrying veteran workflow-context fields rather than accepting and ignoring them.
- **Bearer Token Gates**: `/api/regulatory/preflight` and `/api/admin/cache-clear` accept `REGULATORY_SYNC_SECRET` or `CRON_SECRET` (environment-based).

### Encryption & Integrity

- Private secondary/presumptive workflow records are browser-local and schema-bounded, not encrypted workflow cookies.
- `src/lib/workflow-session-crypto.ts` supplies the optional VA-account sandbox store's AES-256-GCM envelope primitives; that store uses the separate `VA_ACCOUNT_SESSION_SECRET`. The legacy `WORKFLOW_SESSION_SECRET` is checked by `/runtime-readiness` and `/api/health`, but is not a research-workflow secret or the VA-account encryption key.

### Content Security Policy

- **Per-Request Nonce**: Edge middleware (src/proxy.ts) injects a unique nonce on every response
- **script-src**: Does not use `'unsafe-inline'`; relies on nonce for Next.js framework scripts
- **connect-src**: `'self'` only; no third-party CDNs, analytics, or telemetry SDKs
- **wasm-unsafe-eval**: Narrow allowance for in-browser OCR (Tesseract.js WASM) only
- **Other Directives**: frame-ancestors 'none', object-src 'none', base-uri 'self', form-action 'self'

### Security Headers

- **Referrer-Policy**: no-referrer (prevent referrer leakage)
- **X-Content-Type-Options**: nosniff
- **X-Frame-Options**: DENY (clickjacking prevention)
- **Strict-Transport-Security**: max-age=31536000; includeSubDomains (HSTS)
- **Permissions-Policy**: camera=(), microphone=(), geolocation=(), payment=(), usb=() (disable unnecessary APIs)

### Data Boundaries & Privacy Enforcement

- **No Client-Side Analytics**: No Google Analytics, Mixpanel, or similar SDKs; `connect-src 'self'` (prod) in CSP `proxy.ts` + `next.config.ts` headers
- **Operational logging**: allowlisted recommendation and application events are written to platform logs; client error boundaries emit content-free component/status events, and failed recommendation traces use fixed content-free errors. Host retention/access and any enabled tracing collector still require operator review.
- **Browser-Only Evidence (enforced)**: Raw bytes/text never hit `/api` or any server-side session write; processed only via `LocalEvidenceAnalyzer` WASM (`pdfjs-dist` + `tesseract.js` same-origin `/public/tesseract/*` + `mammoth`), retained only as `EvidenceAnalysis` excerpts in `sessionStorage:evidence-analysis:v1` (tab-scoped, `STANDARD_LIMITS.storedBytes=256KB` → `EXTENDED 3MB` budget, `serializeStoredEvidenceWithInfo` trims oldest, `loadStoredEvidence` fail-closed) + `evidenceGapReviewStorageKey` (local checklist); `audit:evidence-architecture` + `ingestion-privacy` tests fail if evidence reaches server
- **Clean URL History**: Browser-local workflow state is not serialized into query/history/referrer; public regulatory snapshot ids and fixed validation codes are non-context route parameters, not user health fields
- **State Scope & Lifetime**: both secondary and presumptive workflow records are browser-local, versioned, schema-bounded, and scoped to `sessionStorage`; successful tab removal ends the browser storage lifetime. Failed writes surface locally rather than sending state to the server. Neither workflow cookie is written or read; the edge proxy expires stale `secondary-workflow-v2` and `presumptive-workflow-v1` presentations with path-scoped tombstones.

### Rate Limiting & Edge Security

- **Vercel Edge WAF**: Automatic DDoS protection and IP-based rate limiting on Server Actions, registered API policies, and public-reference page reads (deployment control requires independent verification)
- **VA API budgets (process-local only, fail-closed in production/distributed):** `VA_API_OUTBOUND_WINDOW_MS=60000` / `VA_API_OUTBOUND_MAX_REQUESTS_PER_SERVICE=60` via `claimOutboundRequestSlot(service)` in `sandbox.ts`; `VA_REFERENCE_CACHE_TTL_MS=300000` LRU-32; `vaProcessLocalStateAllowed()` (`production` or `VERCEL|AWS_LAMBDA_FUNCTION_NAME|FUNCTIONS_WORKER_RUNTIME|K_SERVICE` → live fetch + cache refuse, `VA_SHARED_STATE_REQUIRED_ERROR`); circuit breaker `FAILURE_THRESHOLD=5` → `open 60s` → `half-open` probe (`src/lib/va/circuit-breaker.ts`) gates `requestVaJson` before fetch
- **Application-level route policies:** `src/lib/api-route-policies.ts` owns the API route → limiter mapping as data — `API_ROUTE_LIMIT_POLICIES` (`/api/regulatory/preflight` → `regulatory-preflight` 5/min, `/api/admin/cache-clear` → `admin-cache-clear` 5/min, `/api/health` → `health` 30/min, `/api/auth/login` → `account-auth-login` 30/min, `/api/auth/callback` → `account-auth-callback` 10/min, each carrying its own 429 body and a recorded rationale), `API_ROUTES_WITHOUT_LIMITER` for documented exemptions, and `compileApiRoutePattern` / `findApiRouteLimitPolicy` so `proxy.ts` and the coverage test apply one matching rule (anchored exact match, `[param]` = exactly one non-empty path segment, following the Next.js folder convention) instead of two that could drift; `src/lib/rate-limiter.ts` remains the fixed-window primitive (`createRateLimiter({windowMs,max,name})`, sweep above 10k buckets; documented 2× boundary burst, not a sliding guarantee). Client identity comes from `resolveClientKey(headers)` → `{key: string | null, source: "x-forwarded-for"|"x-real-ip"|"invalid"|"none"}`, which takes the first usable hop of `X-Forwarded-For` and falls back to a usable `X-Real-IP`; *usable* means `isIpLiteral` (IPv4/IPv6), so a hostname, path fragment or fresh random token cannot mint a private bucket — an earlier revision bucketed on any token, and a still-earlier one put every unattributed request in a single `"unknown"` bucket that silently turned the configured per-IP allowance into a global cap one client could exhaust for everyone. `chargeAdmission(limiter, clientKey, env)` charges the shared ceiling (`RATE_LIMIT_UNATTRIBUTED_MAX`, default 6000/60s, the same number `rateLimitScope().ceiling.max` reports) and then the per-client bucket when one exists, returning `refusedBy: "ceiling"|"per-client"|null`; the ceiling is charged for attributed requests too, because a client presenting a different valid IP per request is otherwise unbounded. `rateLimitScope(env)` reports `per-instance` vs `single-process`, plus the identity policy (`RATE_LIMIT_TRUSTED_INGRESS`), that ceiling, and the store regime (`mode: "process-local"`, `blockedBy: "no-store-provisioned"` — no shared counter store is provisioned or wired, so no deployment-wide quota is claimed), and all of it is surfaced as `components.rateLimit` on `/api/health`; this module reads the same `isDistributedRuntime` fact as the VA cache but does **not** fail closed on it, because a limiter that permits more than intended is weaker, not wrong, and disabling it in production would remove defense-in-depth. `tests/api-route-rate-limit-coverage.test.ts` derives the real routes from `src/app/api/**/route.ts` — patterns and exported handler methods read from disk — and fails when a route is neither policed nor explicitly exempt, when a policy names a route that no longer exists, when two policies could both match one request, or when the proxy stops consulting the registry
- **Regulatory Preflight:** `REGULATORY_PREFLIGHT_SOURCE_TIMEOUT_MS=8000` per-source (`http.ts` `AbortController`) + bounded server-local cache `latest.json` + `snapshots/` capped at 20 via atomic write `fs.writeFileSync→renameSync` (`cache.ts`), plus `check-deploy-freeze` provider guard in CI

## API Design

### Server Actions (bounded public operations — `use server` + `server-only` unless noted)

Two Server Actions remain, both public-reference only and both returning their result as action
state rather than redirecting: `searchAccreditedRepresentatives` in
`src/lib/actions/accredited-representatives.ts` (validated public-directory lookup) and
`searchVaFormsFinder` in `src/lib/actions/va-forms-finder.ts` (bounded public form-metadata search).
For both, the visitor's search text or lookup ZIP travels in the request body, so audit A01's
URL/history exposure is closed for these surfaces.
The secondary and presumptive workflow actions were retired: the browser validates and updates
private workflow records locally. API routes provide health, protected regulatory preflight,
protected cache administration, and CSP reporting; they do not accept veteran context.

```
Client-side `/presumptive` submit → validate the service-history draft, persist the browser-local record, then navigate to `/presumptive/results`
Server Action `searchAccreditedRepresentatives(prevState, FormData)` → bounded public zip/radius/type directory lookup; returns the view as state (no URL, no redirect); no Veteran workflow context
Server Action `searchVaFormsFinder(prevState, FormData)` → bounded public form number/keyword/title search; returns the view as state (no URL, no redirect); no Veteran workflow context
```

- **Browser-local secondary steps (no Server Action — PRIV-01 stage 2):** the six `/secondary/*` steps validate and persist entirely in the browser via `src/lib/secondary-workflow/client-steps.ts` → `src/lib/secondary-workflow/browser-context.ts` (`sessionStorage`); no request carries diagnoses, service-connected answers, ratings, medications, treatments, or history. The server serves only uniform public data (client corpus, scope-free regulatory snapshot, public VA reference). Completion/restart are client-side clear-all + navigate.
- **Input:** Both remaining reference actions accept bounded public `FormData` (the finder's text is additionally bounded by `FORMS_FINDER_QUERY_MAX_LENGTH=120` and passes through the PHI-free action-input contract); health, protected regulatory preflight, cache administration, and CSP reporting use their documented API methods. No action accepts secondary or presumptive Veteran workflow context. The retired secondary actions' `appendFormData` helper and Zod bounds now run client-side in `client-steps.ts`.
- **Validation:** `MAX_CONTEXT_ITEMS=20` × `MAX_CONTEXT_ITEM_LENGTH=160`, `MIN/MAX_TIMELINE_YEAR 1900–2100`, `VALID_RATINGS` + `decline→null`, and `serviceHistorySchema` location/date-order rules are enforced in browser-local code; failed writes surface an in-place error without transmitting private context.
- **Output:** The public-directory action returns only public lookup results; browser workflow steps navigate only after a successful local write. Fixed validation codes may be used for user guidance, but private workflow state never appears in URLs, history, or referrers.
- **Security:** The bounded public-directory action uses Next.js CSRF protection and server-only boundaries. Neither workflow writes or reads a workflow cookie; the proxy tombstones stale retired workflow cookies and refuses private-context requests.

- `GET /api/health` — Catalog, ephemeral crypto primitive check, legacy configured `WORKFLOW_SESSION_SECRET` readiness marker, VA config, circuit breakers, knowledge graph and rate-limit policy; `{status:"healthy"|"degraded", components:{catalog,sessionCrypto,workflowSession,kbGraph,rateLimit,vaConfig,circuitBreaker}, ...}` → `200` when required health/readiness components are ready, otherwise `503`; no secret values returned. The workflowSession component is not a check of research-workflow persistence or VA-account store configuration.
- `/va-account/oauth/{ratings|claims}/{start|callback|disconnect}` — separately gated, sandbox-only account flow. `POST start/disconnect` requires exact same Origin; `start` also requires bounded form consent. `GET callback` consumes the one-use state transaction and browser-binding cookie. Responses are private/no-store and redirect to a fixed local notice.
- `/api/auth/login` + `/api/auth/callback` — thin adapters over the same sandbox account flow (claims service) for the restricted-API integration: `GET login` mints the transaction and 303-redirects to the verified authorization URL with a binding-only cookie; `GET callback` redeems once and sets the byte-identical session artifact. Separately rate-limited (see above). Live round trips still land on the canonical callback until VA registers the adapter URL.
- `GET /api/regulatory/preflight` — `Authorization: Bearer {REGULATORY_SYNC_SECRET|CRON_SECRET}` via `timingSafeEqual`; `401` + `auditLog("regulatory-preflight-unauthorized")` on fail; else `refreshRegulatoryPreflightCache()` → `auditLog("regulatory-preflight-triggered", count)` → `{ok:true, snapshotId, finishedAt, freshness, reviewMode, legalRegulatoryConclusionsAllowed, changeCount, relevantChangeCount}`. Used by scheduled `regulatory-intelligence` workflow.
