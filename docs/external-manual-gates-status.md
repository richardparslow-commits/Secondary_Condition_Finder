- **Runtime Logs** — the log-detail list includes **"Search Params" — "Search parameters of the request path"**: <https://vercel.com/docs/logs/runtime>
- **Log Drains reference** — the `proxy.path` field is documented as **"Request path with query parameters"**, with the example `/dynamic/some-value.json?route=some-value`: <https://vercel.com/docs/drains/reference/logs>

Two consequences follow, and both are the finding rather than a caveat: on no documented plan is there a setting that removes `code`, `state` or query parameters from runtime logs or from a drain, and the one document that *does* describe removing a query parameter describes it for analytics events only.

**Findings, each dispositioned.**

- **F1 — the platform documents no query-parameter scrubbing.** Runtime Logs expose a request's search parameters and a drain carries `proxy.path` with its query parameters; there is no documented redaction control for either, and the one filter that does remove a query parameter removes it from analytics events. **Disposition: accepted as a platform limitation.** No setting exists to enable on any documented plan, and no repository change can remove a request line from platform logs. The earlier gate B procedure told an operator to "check whether any configured scrubbing rule removes `code`, `state` or all query parameters"; that instruction had no honest negative answer, and the [inventory](hosting-log-and-callback-inventory.md) Part 4 now records the finding instead of looking for the rule.
- **F2 — the request line is recorded whether or not the request is answered**, so disabling the sandbox or failing closed does not keep it out of the logs. **Disposition: accepted; bounded by reachability rather than by scrubbing.** Both callback handlers return a fixed `503` **before reading any query parameter** when the sandbox config is absent (`src/app/api/auth/callback/route.ts` checks config, store and origin ahead of any `searchParams` read; `/va-account/oauth/{service}/[operation]` returns `null` from `context()` for an unconfigured sandbox). While the sandbox is disabled there is no live code in existence, so a logged request line can only carry an attacker-supplied or stale value.
- **F3 — any retained value is already dead when it is read.** `completeAccountLogin` compares the incoming `state` against the stored transaction and **consumes it single-use before the token exchange** (`src/lib/va/account/oauth.ts`), the callback is bound to an HttpOnly transaction cookie, every outcome is a fixed notice code, and every callback response is `private, no-store` with `Referrer-Policy: no-referrer` — so a replay or a CSRF-crafted callback fails closed and the code-bearing URL cannot leak onward through a `Referer` header. **Disposition: verified code-side and pinned.**

**Residual accepted by the accountable owner on 2026-10-15.** Callback request lines — with `state`, and with any live `code` while credentialed hosted use is enabled — are retained in the platform's logs and in any account-configured drain for whatever retention is in force, and **cannot be scrubbed through any documented setting**. That is accepted for the current deployment, where the sandbox is opt-in, not armed, and no live code can exist, and it is **blocking for credentialed hosted use**: both H-02 gates must be read from the account before that use is enabled, which is why this trigger is preserved rather than discharged.
